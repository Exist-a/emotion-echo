## §一 项目背景与改造目标（沿用 v0.1，§1.3 修订）

### 1.1 现状

当前情绪疏导项目采用纯云端 API 调用模式：

- 用户对话数据全部上传至云端大模型进行推理
- 依赖网络环境，弱网/无网场景下无法使用
- 持续产生 API 调用成本，随用户量增长线性上升
- 情绪疏导属于高度隐私敏感场景，数据上云存在用户信任顾虑

### 1.2 改造目标

将纯云端 API 模式改造为**「端侧优先 + 云端兜底」的混合推理架构**：

| 维度 | 改造前 | 改造后 |
|------|--------|--------|
| 推理位置 | 100% 云端 | 端侧优先，复杂场景云端兜底 |
| 数据隐私 | 对话数据上传云端 | 视 §十二决策 1 而定（(a) 推理本地 / (b) 全程本地） |
| 网络依赖 | 必须联网 | 离线可用（按 §5.5 分层范围），弱网体验不受影响 |
| 响应延迟 | 受网络波动影响（500ms~2s+） | 端侧首 token 百毫秒级，无网络抖动 |
| 调用成本 | 每次对话均产生 API 费用 | 70%+ 对话由端侧处理，大幅降低成本 |
| 用户信任 | 隐私顾虑 | 端侧回答带「本地完成」角标，卖点显性可见 |

### 1.3 核心设计原则（v0.2 修订）

1. **端侧优先**：能在端侧处理的对话绝不走云端，最大化隐私与成本收益
2. **降级有感、错误无感**：~~无感降级~~ → 端侧完成态**显性角标**；切换本身平滑不中断（大厂先例：Apple 转第三方显式弹窗、Gemini 端侧任务有标识 —— 完全静默会让用户对「永不离设备」产生错误预期）
3. **渐进式落地**：分阶段实施，先验证可行性，再逐步扩大端侧覆盖比例
4. **体验不降级**：端侧模型在情绪疏导核心场景下的回复质量需达到可用标准（以 §六.6 golden set 为准绳）
5. **〔v0.2 新增〕测试可先行**：路由决策 / 关键词表 / 降级状态机 / token 预算必须是纯函数 + 引擎接口注入，WebGPU 真机只进浏览器 E2E —— 符合 AGENTS.md「测试不依赖浏览器/网络」硬规则与既有「浏览器 API 依赖走字面量契约测试」决策

## §二 技术选型（v0.1 + v0.2 修订）

### 2.1 端侧推理引擎：WebLLM（✅ 已核实，维持主力）

**选型理由（v0.2 逐条核过源码）：**

- MLC 团队出品，基于 WebGPU 硬件加速，浏览器端性能最优的 LLM 推理方案
- **100% 兼容 OpenAI API 格式**（`src/config.ts` 确认 openai_api_protocols），本项目云端链路本就 OpenAI 兼容（`downstream/llm.go:101`），插一个适配层即可
- 支持流式输出、**Web Worker 后台线程隔离**（`CreateWebWorkerMLCEngine`）、模型本地缓存（**Cache / IndexedDB / OPFS 三后端可选**）
- 预置 Qwen 系列模型表（0.5B~9B，含 vram 标称与 `low_resource_required` 标记），**可零编译直接用**
- 比纯 CPU 推理快 5~10 倍

**备选方案对比（沿用 v0.1）：**

| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| WebLLM | 性能最优、API 兼容、生态成熟 | 需自定义编译模型（预置表可绕过） | **主力方案** |
| Transformers.js + GGUF | 无需编译模型、上手快 | 性能比 WebLLM 低 30%~50% | 原型验证备选 |
| ONNX Runtime Web | 通用性强、微软背书 | LLM 优化不如 WebLLM 深入 | 不推荐 |

### 2.2 端侧模型：MindChat **降级为待验证**（❌ v0.1 谱系错误，v0.2 修订）

**v0.1 原文问题**：称 MindChat-Qwen2 有「0.5B / 1.8B / 4B / 7B 多参数版本」——**1.8B 与 4B 是 Qwen1.5 的尺寸，Qwen2 基座没有这两个规格**，两个系列的谱系被记混了。且 MindChat 项目 2024 年初后未见活跃更新。

**v0.2 修订后的选型策略（双轨，阶段一 A/B 后定）：**

| 候选 | 依据 | 状态 |
|------|------|------|
| **WebLLM 预置 Qwen3-1.7B / Qwen3.5-2B（q4f16_1）** | 预置表零编译、显存标称 ~2.0-2.2GB、基座活跃维护；情绪疏导适配靠 §六强约束 prompt | **阶段一默认先跑**（当天可出 Demo） |
| MindChat-Qwen2 0.5B / 7B（实际存在规格） | 心理垂直微调，若质量显著优于通用基座则采用 | 阶段一验证：**存在性 + license + 与预置基座同题对比**，任一不过即弃 |
| 分级加载（沿用 v0.1 思路） | 0.5B 级做移动端/低配降级、1.7~2B 级做桌面主力 | 维持 |

> **教训固化**：v0.1 的版本号是凭记忆写的 —— 印证 AGENTS.md 文档功课④「版本号必须从权威源核实」。选型相关数字一律以 WebLLM `src/config.ts` 与模型仓库页面为准。

### 2.3 云端兜底 API（沿用 v0.1）

- 保留现有云端 API 调用链路不变（BFF 已有 gRPC→HTTP→mock 三级降级骨架，`ai_stream_handler.go`，端侧可作为其「第 0 级」插入）
- 仅在端侧无法处理或设备不支持时触发

## §三 总体架构设计（v0.1 图 + v0.2 增量）

### 3.1 架构图（v0.2 增补离线队列与本地存储）

```
┌─────────────────────────────────────────────────────────┐
│                      用户交互层                            │
│  聊天界面 / 情绪记录 / 历史管理 / 设置中心                │
└──────────────────────────┬──────────────────────────────┘
                           │

│              混合调度引擎（前端单点插入口）                 │

│  ┌─────────────┐  ┌──────────────┐  ┌───────────────┐ │
│  │ 设备能力检测 │→│ 对话复杂度判定 │→│ 路由决策       │ │
│  │ WebGPU/显存 │  │ 意图/长度/风险│  │ 端侧 or 云端  │ │
│  └─────────────┘  └──────────────┘  └───────┬───────┘ │

              ┌────────────┴────────────┐
┌─────────────▼──────────┐  ┌──────────▼──────────────┐
│    端侧推理层           │  │    云端 API 层           │
│  WebLLM（Worker 隔离）   │  │  现有 BFF→llm-service    │
│  本地模型权重（缓存后端） │  │  → OpenAI 兼容 API       │
└─────────────────────────┘  └──────────────────────────┘
```

### 3.2 核心模块说明（v0.2 增补后）

| 模块 | 职责 |
|------|------|
| **设备能力检测** | 页面加载检测 WebGPU、可用显存、设备类型，决定可加载模型等级 |
| **对话复杂度判定** | 轻量分析（意图、文本长度、风险关键词），判断是否适合端侧 |
| **路由决策** | 综合设备能力 + 复杂度 + 端侧模型健康态，决定端侧/云端（决策树见 §5.1） |
| **端侧推理层** | WebLLM 封装：模型加载、缓存管理、Worker 隔离、流式推理 |
| **云端 API 层** | 复用现有链路，作为兜底通道（现有三级降级骨架的上游） |
| **降级与回退** | 端侧失败/超时/显存溢出自动切云端，对话不中断 |
| **〔新增〕离线层** | Dexie 消息缓存 + outbox 待发队列 + 重连补发（§5.5） |
| **〔新增〕prompt 统一组装层** | 端云共用同一组装链，按 profile 切换指令风格/历史策略/护栏开关（§六.5） |

**插入口证据（为什么改造成本低）**：前端全站只有 `useAIStreamHandler.sendAIStream` 一个取回复函数（唯一调用方 `useConversationSender`）；BFF 端 `ai_stream_handler.ServeHTTP` 已有 gRPC→HTTP→mock 三级降级骨架，端侧天然是「第 0 级」。两处插入口都不需要动页面。

## §四 端侧模型部署方案（v0.1 + v0.2 修订）

### 4.1 模型获取与编译（v0.2 修订：预置优先 + CDN 补 wasm）

```
优先路径（零编译）：
  直接采用 WebLLM 预置 Qwen3 系模型（src/config.ts 模型表），跳过编译

需要自定义时（MindChat 若验证通过 / 特殊量化）：
  步骤 1：下载原生模型（HuggingFace / ModelScope）
  步骤 2：MLC-LLM 编译量化
     mlc_llm compile --target webgpu --quantization q4f16_1 ...
  步骤 3：产物上传自有 CDN + CORS + gzip/br + 分片传输
```

**编译产物清单（v0.2 补全 —— v0.1 漏了 wasm）：**

- 量化模型权重分片（`.params`，预置 1.7B 级 ~1GB 内）
- `mlc-chat-config.json` + `tokenizer.json` / `tokenizer_config.json`
- **〔v0.2 补〕模型库 wasm（`model_lib`）**：WebLLM 默认从 `raw.githubusercontent.com` 拉 wasm、从 `huggingface.co` 拉权重，**国内均不通** → `modelLibURLPrefix` 与权重地址必须一并指向自有 CDN（`src/config.ts` 支持自定义 `model_list` + `model_lib` URL）

### 4.2 模型加载与缓存策略（沿用 v0.1）

```
首次访问：设备能力检测 → 进度条（下载）→ 缓存后端落盘 → WebGPU 内核编译 → 就绪
二次访问：直接读缓存 → 跳过下载 → 内核编译（1~3 秒）→ 就绪
```

- 缓存后端在 WebLLM 的 Cache / IndexedDB / OPFS 中按实测定（`src/config.ts` 注明 Cache API 最成熟）
- 版本号标识自动清理旧缓存；提供「清除本地模型」入口；存储不足提示并降级云端

### 4.3 Web Worker 隔离（沿用 v0.1）

- 模型加载与推理全部在独立 Web Worker（`CreateWebWorkerMLCEngine`），主线程只管 UI 与消息转发
- 流式输出经 postMessage 增量推主线程 → 直接喂现有打字机管线（`useConversationSender` onDelta 累加已存在）

## §五 混合调度策略（v0.1 + v0.2 修订）

### 5.1 路由决策逻辑（v0.2 补「高危×离线」分支）

```
用户输入
  │
  ├─ 设备不支持 WebGPU？ ──────────── 是 → 云端 API
  │
  ├─ 端侧模型未加载完成？ ────────── 是 → 云端 API（加载完成后切换）
  │
  ├─ 命中一级高危关键词？（自杀/自残/不想活…）
  │     ├─ 联网 → 云端 API（专业处理）+ 弹援助热线提示
  │     └─ 离线 → 【v0.2 新增】端侧硬规则路径：
  │                直接弹援助热线（400-161-9995 等）+ 固定危机回应模板，
  │                **不依赖模型判断、不依赖网络** —— 兜住「高危×断网」交叉格
  │
  ├─ 输入文本超长？(>500字) ──────── 云端 API
  ├─ 需要复杂推理/多步逻辑？ ─────── 云端 API
  ├─ 断网状态？ ──────────────────── 端侧（L0 范围内；见 §5.5 分层）
  │
  └─ 以上均否 ─────────────────────→ 端侧推理
```

### 5.2 端侧适用场景（沿用 v0.1）

日常情绪倾诉与倾听 / 简单安抚共情 / 放松呼吸引导 / 睡眠压力常识问答 / 单轮 <500 字短对话。

### 5.3 云端兜底场景（沿用 v0.1 + 补充）

高危危机干预 / 深度心理分析与专业干预 / 超长文本与长上下文多轮 / 用户主动「深度模式」/ 端侧失败或超时（>10s 无响应）/ **联网且复杂度超端侧能力的任何场景**。

### 5.4 切换与告知（v0.2 修订「无感降级」）

```
端侧推理发起
  ├─ 10 秒内首 token？ ── 否 → 中断端侧切云端，对话不中断
  ├─ 推理中报错/显存溢出？ → 自动切云端 + 提示「正在为你切换更专业的模式」
  └─ 正常完成 → 返回端侧结果 + 【v0.2】气泡角标「本地完成」
```

v0.1 的「用户完全无感知」修订为：**过程平滑无感、来源显性可见**（对照 §1.3 原则 2）。

### 5.5 离线能力分层与四问题（v0.2 新增）

端侧化必然伴随离线场景。拆为四个必须解决的问题：

1. **断网消息堆积补发（outbox 模式）**——地基已有一半：Dexie `getPendingMessages`/`getFailedMessages`（`messageCache.ts`）、服务端 `clientMsgId` 幂等（`sendmessagelogic.go`）、online 事件钩子（`plugins/init.ts`，重试逻辑尚为 TODO）。缺：flush 循环（按 sendTime **保序** + 指数退避）、气泡「待发送/发送失败」状态 UI。
2. **无网络功能可用**——三个子问题：
   a. 端侧推理可用（以模型已缓存为前提）；
   b. 会话与历史可用（新建会话/拉历史现依赖服务端 → 按下表分层）；
   c. **登录态**：离线无法刷新 JWT，token 过期则全部离线能力连同端侧推理一起失效 → 需离线宽限期 / 提前刷新（v0.1 未覆盖）。
3. **端侧 AI 回复补传**——现状 AI 回复由 BFF 流式结束同步入库（`saveAIMessage`），离线时该步不存在；若只补传用户消息，会出现「多条用户消息、0 条 AI 回复」的残缺历史。需要**新的服务端契约**：客户端携带完整离线回复 POST + 幂等 + 保序。**该契约是否存在取决于 §十二决策 1**：选 (a) 需要且补完后报表/历史零感知；选 (b) 不需要但面临本地/服务会话双轨架构。
4. **多端乱序/冲突**——单设备为主可暂缓，但「补发保序 + clientMsgId 幂等」两条规则第一天立好，否则日后补不齐。

**「离线可用」验收分层（防范围失控）：**

| 层 | 离线能力 | 依赖 |
|----|----------|------|
| **L0（必须）** | 已有会话内正常对话 + 断网消息排队重连补发 | outbox + 端侧模型 + AI 回复补传契约 |
| **L1（应做）** | 浏览已同步过的历史 | Dexie 缓存接线（基建已有） |
| **L2（可选，二期）** | 离线新建会话 + 重连 reconcile | 临时会话 ID 机制，工作量大 |
| **不可用（显式降级）** | 报表 / 测评 / TTS / 数字人 / 新设备登录 | 云端服务，给「联网后可用」提示 |

## §六 情绪疏导场景专属优化（v0.1 + v0.2 方法论增补）

### 6.1 强约束 System Prompt（沿用 v0.1）

```
你是一名温暖、专业的心理疏导伙伴，名叫「小暖」。

核心原则：
1. 倾听优先：先共情用户的情绪，再给出建议，不急于评判或说教
2. 温和包容：使用温暖、柔和的语言，让用户感到被理解和接纳
3. 不做诊断：不进行心理疾病的诊断，不推荐处方药
4. 引导表达：通过开放式问题引导用户表达内心感受
5. 积极关注：关注用户的积极资源和应对能力，给予肯定和鼓励

安全边界：
- 如用户表达自伤、自杀或伤害他人的想法，立即严肃对待，
  建议其拨打心理援助热线（如 400-161-9995）或寻求专业医疗帮助
- 不替代专业心理咨询师的工作，复杂问题建议线下就医

回复风格：
- 每次回复 100~300 字，简洁温暖
- 适当使用语气词，避免生硬的书面语
- 结尾可提出一个温和的开放式问题，促进继续表达
```

### 6.2 上下文管理（沿用 v0.1 + v0.2 分层记忆设计）

v0.1 原则维持：保留最近 6~8 轮、超阈值摘要压缩、`max_tokens ≤512`、对话摘要仅存本地。

**v0.2 分层记忆设计（端云共用，token 硬预算）：**

```
L0 当前轮 user 消息        — 永远保留
L1 滑动窗口最近 3-4 轮原文  — 端侧窗口开小（小模型长上下文注意力衰减快）
L2 滚动摘要（每 K 轮压一次） — "前 10 轮聊了工作压力+搬家，基调从焦虑转平稳"
L3 结构化事实卡片           — 抽取式（不生成）："提到过：项目 deadline、怕黑"
```

- **Token 硬预算**（工程约束，非调参）：system ≤400 / 历史 ≤600 / 输出留 512；超预算按 L3→L2→L1 顺序裁剪，实现为纯函数可单测
- **谁来压缩**：L3 事实卡片用规则/正则抽取，**不经过模型** —— 零幻觉、离线可用、几乎不耗算力；L2 摘要可搭云端回复的便车（走云端那轮顺带生成），纯端侧轮次降级为只更新 L3
- **摘要存哪**：随 §十二决策 1 —— 选 (a) 可服务端生成下发；选 (b) 必须本地且接受换设备失忆
- **端云共用同一份组装层**：记忆/摘要从第一天就由同一组装层喂两边，避免上下文割裂
- **明确不做**：不给端侧硬灌长上下文、不上 RAG —— 1.5B 级模型长上下文利用差，token 花了质量不涨；端侧定位就是 §5.2 短对话场景

### 6.3 本地风险关键词兜底（沿用 v0.1，接入 §5.1 高危×离线分支）

- 一级高危（转云端 + 弹热线；**离线时直接弹热线+固定模板**）：自杀、自残、不想活、结束生命、伤害自己等
- 二级关注（转云端）：抑郁确诊、焦虑症、创伤经历、家暴等
- 本地毫秒级匹配，不依赖模型判断

### 6.4 本地轻量知识库（可选二期，沿用 v0.1）

几百条疏导方法/放松技巧/睡眠建议，端侧关键词检索增强，几乎零算力开销。

### 6.5 提示词优化方法论（v0.2 新增）

端侧小模型与云端的能力差距，靠三件事结构性地补（prompt 工程只能拉到「场景内可用线」，**质量最终保证是路由兜底**）：

1. **指令扁平化 + few-shot 化**：现有护栏是复合否定嵌套（「不点破来源；不贴标签；调整要有感但不过火」，`personality_directive.go`）——云端强模型能遵守，小模型大概率崩。端侧改法：一条指令一个行为、全改正面表述；准备 2-3 组黄金示例对（用户输入→理想回复），**小模型模仿示例远强于遵循抽象指令**（示例吃 token，与 L1/L2 历史抢预算，需 A/B）
2. **护栏从「模型自觉」改为「代码兜底」**：端侧最重要的范式转换 —— 输出后跑确定性检测（贴标签词/诊断词/热线缺失/长度超限），命中即截断、替换或重生成；高危回应直接给模板填空，而非嘱咐模型「请严肃对待」。护栏通过率从此变成可断言指标
3. **人格段端侧走最窄路径**：`buildPersonalityGuide` 的 ipsative 回退本就收敛到「相对最高+相对最低」两条，端侧固定走此路径不带 5 条全量。E2E-14 沉淀的「指令写可观察输出特征、去标识盲判验收」方法论恰好小模型友好，直接继承（关联 ADR `personality-prompt-semantics`）

### 6.6 评测体系 golden set（v0.2 新增 —— 「一段时间优化」的组织方式）

开放式「调到好」不可验收，按里程碑切：

- **评测集先行**：v0.1 阶段一的「20 组典型对话」扩为 golden set —— 按场景分层（日常倾诉/高危/超长输入/人格各分档/情绪各态），每组带期望特征
- **自动指标**：护栏通过率、长度合规率、指令遵循度（可断言）；情绪贴合度走去标识盲判（E2E-14 已验证）
- **回归纪律**：prompt 每次改动跑 golden set 回归 —— prompt 变更按测试对待
- **里程碑**：① golden set 基线跑通（端侧水平有数）→ ② 护栏代码兜底上线（通过率 ≥ 阈值）→ ③ few-shot/扁平化迭代到端侧场景可用线。①②不依赖模型选型落定，**可提前并行开工**

> **心理赛道无端侧先例**（§十一调研）：Woebot/Wysa 等全为云端 —— 质量责任无人替我们踩坑，golden set 是唯一把「够不够好」变成客观问题的手段。
