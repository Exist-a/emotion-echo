## 一、一句话定位

**Emotion-Echo 是一个「分布式架构 + 单机部署」的系统**——架构是按微服务风格拆分的真分布式,部署形态是单机多实例(集中式)。

更具体地讲:
- **架构风格**:微服务(按业务能力拆分,服务独立 schema,服务间异步通信 + 同步调用)
- **部署形态**:单机多实例(1 台 ECS 上跑多个容器,同一镜像可能起 2-3 个实例)
- **集群模式**:真集群(Nacos 自动发现、Kafka 多 partition、多 consumer group)

这三个维度**独立可组合**,本项目的组合是 **「微服务 + 单机 + 真集群」**。

---

## 二、术语澄清:这不是「伪分布式」

很多人看到「单机多实例」会条件反射地说「这是伪分布式」——**这个判断不适用于本项目**。

「伪分布式」是个**特定术语**,指 Hadoop/Spark 那种「框架本来设计给多机用,为了演示硬塞到单机跑」的情况。这些框架在单机上跑会暴露各种 bug 和不一致——它们是**真分布式系统的妥协**。

本项目**不属于这种情况**:

| 维度 | 伪分布式(典型) | 本项目 |
|---|---|---|
| 框架设计目标 | 多机 | 单机 / 多机皆可 |
| 单机上能完整运行吗 | ❌ 各种 bug | ✅ 是设计目标之一 |
| 部署到多机会改变行为吗 | 会(暴露出原设计的多机假设) | 不会(只是资源上限不同) |
| 单机多实例的真实含义 | 框架妥协 | **架构标准选项** |

**正确表述是「单机部署的分布式架构」**,不是「伪分布式」。国内外很多博客乱用这个词,需要警惕。

## 三、架构三层(风格 / 部署 / 集群)

| 维度 | 选项 | 本项目选择 |
|---|---|---|
| **架构风格** | 单体 / 微服务 / Serverless / Modulith | **微服务** |
| **部署形态** | 单机 / 多机 / 多 region | **单机(集中式)** |
| **集群模式** | 真集群 / 玩具模式 | **真集群** |

### 三维度的独立含义

- **架构风格**:决定代码怎么组织、团队怎么分工、API 怎么定义
- **部署形态**:决定资源怎么分配、容灾能力、运维复杂度
- **集群模式**:决定中间件怎么用(Nacos 真集群 / 单点、Kafka 多 broker / 单 broker)

三个维度**不绑定**:
- 「微服务 + 单机」✅ 完全合理(80% 生产业务)
- 「微服务 + 多机」✅ 大型生产业务
- 「单体 + 多机」✅ 也有(传统大厂遗留)
- 「单体 + 单机」✅ 中小项目

## 四、单机能学到的架构能力(90%+)

单机多实例**几乎能学到分布式架构的全部核心能力**:

| 能力 | 单机多实例能学到 | 说明 |
|---|---|---|
| 服务边界设计 | ✅ | chat / ai / user / analytics / assessment 各服务独立 |
| 服务间通信(HTTP / gRPC / Kafka) | ✅ | 跨进程调用 + 异步事件 |
| 服务发现(Nacos) | ✅ | 多实例自动注册,Nacos 看到所有 |
| 配置中心(Nacos) | ✅ | yaml 不够,配置走 Nacos |
| 负载均衡(Nginx upstream) | ✅ | 多实例轮询 + 健康检查 |
| 故障自愈(实例级) | ✅ | Docker `restart: always` + 健康检查 |
| 滚动更新 | ✅ | 逐个 stop / start,零停机 |
| Kafka partition + rebalance | ✅ | 多实例 consumer 分配不同 partition |
| API 网关 | ✅ | Nginx / APISIX 路由 |
| 微服务治理(限流、鉴权、链路追踪) | ✅ | APISIX / Nginx + JWT |
| 跨服务数据一致性(outbox + event_id 去重) | ✅ | at-least-once + 幂等 |
| 物化视图跨 schema 聚合 | ✅ | analytics-svc 引用 ai-svc schema |

**对学习目的,单机多实例足够覆盖分布式架构的几乎所有核心模式。**

## 五、单机暂时学不到的(到多机时补)

| 学不到 | 何时补 |
|---|---|
| **机器级容灾**(整台机器挂了顶替) | 上多机时 |
| **跨机网络延迟处理**(HTTP / Kafka 跨机延迟) | 上多机时 |
| **磁盘 IO 竞争隔离**(跨机器共享存储) | 上多机时 |
| **分布式限流**(共享 Redis 计数器) | 上多机时 |
| **真负载下的瓶颈转移** | 上多机时 |
| **跨地域部署** | 商业化时 |
| **Kafka ISR / 副本切换**(单 broker 没副本) | 上多机 / 多 broker |

**这部分差距在 5%–10% 之间**——对学习目的不影响,对生产目的需要补。

## 六、单机多实例 vs 多机(差异表)

| 维度 | 单机多实例 | 多机 | 影响 |
|---|---|---|---|
| 服务拆分 | ✅ | ✅ | 一致 |
| 服务发现 | ✅ | ✅ | 一致 |
| 消息队列(Kafka) | ✅ | ✅ | 一致 |
| 负载均衡 | ✅ | ✅ | 一致 |
| 实例级自愈 | ✅ | ✅ | 一致 |
| 滚动更新 | ✅ | ✅ | 一致 |
| 跨服务数据一致性 | ✅ | ✅ | 一致 |
| API 网关 | ✅ | ✅ | 一致 |
| **机器级容灾** | ❌ | ✅ | **不同** |
| **跨机网络行为** | ❌(看不到) | ✅(会暴露 HTTP / Kafka 跨机延迟) | **不同** |
| **真水平扩展** | ❌(单机 CPU/内存上限) | ✅ | **不同** |
| **磁盘 IO 竞争** | 共享(同机) | 独立(不同机器) | **不同** |
| **资源隔离边界** | 进程级(共享 OS) | 机器级(独立) | **不同** |
| **跨地域容灾** | ❌ | 取决于部署 | **不同** |

### 关键差异的具体表现

#### 1. 资源隔离边界

```
单机多实例:
  1 × ECS (8 核 16G)
  ├─ 所有实例共享同一台物理机的 CPU / 内存 / 磁盘
  ├─ 一个实例 OOM 可能影响其他实例(操作系统层内存压力)
  └─ 一个实例 CPU 飙高会抢占其他实例的 CPU

多机:
  N × ECS
  ├─ 每个机器的 CPU / 内存是独立的
  ├─ 一个实例挂了不影响其他实例的资源
  └─ 但磁盘 IO 还是会互相影响(共享存储时)
```

#### 2. 网络行为

```
单机多实例:
  实例A → 实例B: 本地网络(<1ms,几乎不丢包)
  - 看不出网络问题
  - Kafka「跨分区延迟」几乎为 0
  - HTTP 调用不会超时

多机:
  实例A → 实例B: 真实网络(0.5-30ms,可能丢包)
  - 网络抖动会暴露
  - Kafka 跨分区有可见延迟
  - HTTP 调用会偶发超时
```

**实际影响**:单机上看不到的 bug,会在多机上暴露,例如:
- HTTP client 超时设置不合理
- Kafka consumer poll 超时太小
- 重试逻辑太激进
- 限流阈值没考虑跨机延迟

#### 3. 故障域

```
单机多实例:
  - 实例级故障:Docker restart 就能恢复(几秒)
  - 机器级故障:重启整个 ECS(几分钟),全部实例一起死

多机:
  - 实例级故障:同左
  - 机器级故障:流量自动切到其他机器(秒级)
```

## 七、当前部署形态

### 7.1 保留的组件

| 组件 | 当前角色 | 为什么保留 |
|---|---|---|
| **Nacos** | 配置中心 + 服务发现 | 学习价值 + 实际有用,内存占用可控 |
| **Kafka** | 事件驱动主干 | 解耦 chat / ai / analytics,代码兼容 |
| **Helm chart** | K8s 部署工具 | 学习用,实际单机部署不用 Helm |
| **kind** | 本地 K8s | 继续学 K8s 概念(跟单机部署不冲突) |
| **Docker Compose** | 部署工具 | 单机部署的核心 |

### 7.2 弱化或下线的组件

| 组件 | 原角色 | 单机场景的取舍 | 替代 |
|---|---|---|---|
| **APISIX** | API 网关 | 单机偏重,功能过剩 | **Nginx**(反向代理 + HTTPS 终止 + upstream) |
| **SkyWalking** | 链路追踪 | 单机用 docker logs 也行 | **可选保留**(学习价值)或直接用阿里云日志服务 |
| **etcd** | 分布式 KV | 单机不需要 | 直接用环境变量 / Nacos |

### 7.3 单机硬件下限

```
最低配置(关 SkyWalking + 关 Python AI 服务):
  Postgres:   1 GB Kafka:     1 GB
  Redis:      200 MB
  Nacos:      500 MB
  chat-svc:   100 MB
  user-svc:   100 MB
  ai-svc:     300 MB
  assessment-svc: 100 MB
  analytics-svc:  100 MB
  web-bff:    100 MB
  emotion-llm-service: 100 MB
  ─────────────────────
  合计: ~3.6 GB 内存 + 4-6 核

推荐: 4 核 8G ECS 是底线,8 核 16G 更稳
```

## 八、选型理由

### 8.1 学习目的

- 单机多实例能学 **90%+** 的分布式架构核心能力
- 不用一开始就面对多机特有的故障模式(网络分区、机器宕机、磁盘 IO 竞争)
- 学习曲线更平滑:聚焦架构,不被基础设施噪音干扰

### 8.2 业务目的

- 个人作品集 / 练手项目,流量很小
- 业务功能上,单机完全能撑几年
- 多机能提供的「机器级容灾」对当前业务没有实际意义

### 8.3 经济目的

| 形态 | 月成本(阿里云) |
|---|---|
| 单机 4 核 8G | ~300-500 元 |
| 单机 8 核 16G(推荐) | ~600-1000 元 |
| 多机 5 台 × 4 核 8G | ~1500-2500 元 |
| 多机 + 托管中间件 | ~2000-3500 元 |

**单机比多机便宜 3-5 倍**——对练手项目,这是合理的选择。

### 8.4 架构清晰

「分布式架构 + 单机部署」是工程界**公认的标准选项**,不是「架构 vs 部署」的矛盾:

- **架构**:决定**怎么组织代码和团队**
- **部署**:决定**怎么放资源和容灾**

两者独立决策,本项目刻意把两者解耦:
- 架构上保留微服务拆分(学分布式核心模式)
- 部署上选择单机(经济、简单、对练手足够)

## 九、常见问题澄清

### Q1:为什么不直接用 K8s?

**A**:K8s 在单机上**收益几乎为零,代价反而存在**。

K8s 核心价值:多节点调度、自愈、水平扩展、滚动更新、服务发现、配置管理。

单机场景:
- 多节点调度 ❌(只有1 台机器)
- 自愈 ⚠️(`restart: always` 已经覆盖 80%)
- 水平扩展 ❌(单机扩无可扩)
- 滚动更新 ⚠️(Docker Compose 也能做)
- 服务发现 ✅(但 Nacos 已经覆盖)
- 配置管理 ✅(但 Nacos 已经覆盖)

**反而带来的代价**:
- 资源浪费(control plane 占 1-2 GB)
- 嵌套虚拟化(性能损耗 5-10%)
- 复杂度翻倍(Helm + docker-compose 两套)
- 调试变难(kubectl 多一层抽象)

**结论**:单机用 K8s 是**杀鸡用牛刀**。

### Q2:单机能学到的架构能力够吗?

**A**:**对练手/学习目的完全够**——单机多实例能学到分布式架构 90%+ 的核心能力。剩下 10% 是真容灾、跨机网络等运维进阶,这些对学习项目不是必学项。

### Q3:这是不是伪分布式?

**A**:**不是**。详见第二节「术语澄清」。

### Q4:Kafka 单 broker 够吗?

**A**:**当前业务量够**。详细分析见 `distributed-architecture.md` 和 `stage-30-B-kafka-pipeline.md`。要点:
- 当前 ai-svc / analytics-svc 各 1 实例,1 个 partition 即可
- 单 broker 是「玩具模式」,但清醒地知道就行
- 上多机时升级为 2-3 broker + 副本因子 2

### Q5:单机部署需要 Helm 吗?

**A**:**不需要**。Helm 是 K8s 部署工具,单机部署用 docker-compose。

但**保留 Helm chart 作为学习用**——它代表「一旦业务扩到多机,直接 `helm install` 就能部署」的能力。

### Q6:为什么保留 Nacos 而不是直接用 .env?

**A**:**Nacos 的服务发现能力用 .env 替代不了**。多实例注册、动态扩容、配置热推送——这些是 .env 文件做不到的。

### Q7:单机多实例是不是只能学到「分布式逻辑」学不到「分布式故障」?

**A**:**对**。故障自愈(实例挂了)能学到,但机器级故障、网络分区学不到。这些是「运维进阶」,不是「架构核心」。
